Overview

This writeup describes the capture and analysis pipeline behind the RISC-V AES-128 baseline. The objective was not only to recover a key, but to make every step repeatable from immutable evidence: generated plaintext schedules, hashed capture logs, independent acquisition audits, a fixed analysis window, and a held-out verification set.

The pipeline recovered the full key in two independent 1,024-trace sessions and reproduced 16/16 held-out ciphertexts with the recovered key. Every capture, schedule, and report is identified by a hash.

Evidence rules

  • Raw trace arrays are immutable: they are never edited, and each capture log records the hashes of its arrays.
  • Dataset descriptors link the capture log, plaintext schedule, bitstream, and configuration by SHA-256.
  • Machine checks and operator reviews are recorded separately and neither is promoted into the other.
  • Failed attempts are preserved rather than deleted.
  • Analysis outputs are written outside the raw-data directories and refuse to overwrite an existing report.

Balanced plaintext schedules

The schedule generator creates 1,024 plaintexts in which every byte position sees all 256 values exactly four times. Each byte position is permuted independently, then the full list is shuffled with a recorded seed. This keeps every CPA hypothesis uniform while letting one capture session attack all 16 key bytes.

.venv/bin/python capture/scripts/make_riscv_aes_fullkey_schedule.py \
    --output capture/configs/riscv_aes_fullkey_1024_20261120.json \
    --repetitions 4 --seed 20261120

Sessions 1 and 2 used seeds 20261120 and 20261121. The two schedules were checked for zero plaintext overlap before the second acquisition. The generator refuses to replace an existing schedule file, so a seed cannot be silently reused with different content.

Capture and identity checks

Each acquisition starts with a full USB reset and bitstream programming. Before any mailbox write, the host reads the RSCV identity registers and confirms version, core, workload, byte-count width, and window. This prevents a stale or mismatched bitstream from being captured under the wrong label.

Independent acquisition audit

Before any leakage analysis, a separate verifier reloads the capture log and every raw array. It re-encrypts the recorded plaintexts with the public test key and compares all 1,024 ciphertexts, then checks the raw-array hashes and the capture-log hash. The audit re-checked 1,024 ciphertexts and 5,120 raw arrays per session.

The public key is used only for this correctness check. It is never passed to the CPA ranking, and the recovered key is compared with it only after the ranking is complete.

Full-key CPA automation

The analysis script loads the audited traces and recorded plaintexts, computes first-round CPA for all 16 byte positions, and reports results over a trace-prefix grid fixed before the results are observed. The default model is HW(SBox(plaintext[i] XOR candidate)); the additive model is available as an alternative but cannot distinguish a candidate from its 0xFF complement.

  • No alignment, filtering, or rewriting of raw samples.
  • All 256 candidates are scored for every byte.
  • Prefix counts: 16, 32, 64, 96, 128, 256, 512, and 1,024 traces.
  • Disjoint 512-trace halves are ranked separately.
  • The recovered key must reproduce every captured ciphertext before the report is accepted.

The hold-out set contains 16 plaintexts generated with seed 20261122 and verified absent from both attack schedules. They were captured with the same image and re-encrypted with the recovered key only. All 16 ciphertexts matched; the verification record reports identical SHA-256 values for the recovered and reference keys and no mismatches. The held-out count exceeds the project's threshold of ten independent checks.

Preserved failures and operational lessons

  • The first 1,024-trace attempt produced a correct ciphertext but was rejected because its 181,088-cycle count fell outside the then-accepted 181,090–181,096 band. The band was widened to ±100 with that evidence, and the attempt is preserved in the archive.
  • MAX_CYCLES must exceed 181,096; the configured 400,000 prevents a missing completion from hanging the run.
  • A missing AES round differs by about 18,000 cycles, far outside the accepted band.
  • The logic analyzer stores 16,376 samples, so it samples at 1× the target clock for these windows; the ADC counter supplies the measured width.
  • The RSCV identity gate runs before any write, so a stale bitstream cannot be captured silently.

Limitations

  • The pipeline was exercised on one board, one bitstream, one public key, and one measurement configuration.
  • No trace alignment, preprocessing, TVLA, or higher-order analysis is included.
  • The hold-out verification uses the same image and board; it checks the recovered key, not generalization across devices.
  • Reproducibility here means the documented result can be regenerated from the recorded evidence under the same conditions.
