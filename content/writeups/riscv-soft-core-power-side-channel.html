Overview

This writeup documents a first-order correlation power analysis (CPA) against software AES-128 running on a PicoRV32 RISC-V soft-core. The target is the unprotected reference built for a B.Sc. final project on hardware side-channel protection. All measurements were taken on owned lab hardware using the public FIPS-197 test key.

Two independent physical sessions of 1,024 traces each recovered all 16 AES-128 key bytes. In both sessions the complete key was correct at a 96-trace prefix, and the recovered key reproduced every captured ciphertext. The analysis window, leakage model, and trace-prefix grid were fixed before the captures were scored.

Scope and threat model

The experiment assumes an attacker with physical access who can trigger encryptions with chosen plaintexts and observe the board's power consumption. It does not model remote access, fault injection, or a protected implementation. The work is defensive and reproducible: the goal is to establish a measured baseline for comparing hardware countermeasures.

  • Target: software AES-128 on a RISC-V soft-core implemented on an FPGA.
  • Key: the public FIPS-197 test key 000102030405060708090a0b0c0d0e0f, compiled into the firmware image.
  • Access: chosen plaintexts through a USB register bank and a hardware trigger around the first-round SubBytes operation.
  • Out of scope: protected builds, other boards, other keys, and any claim about instruction-level leakage attribution.

The FPGA design uses about 2,003 LUTs, 1,656 flip-flops, and 16 RAMB36 blocks. The routed build closed timing with a worst negative slack of +0.033 ns and a worst hold slack of +0.034 ns.

Vulnerable workload and trigger

The workload is a straightforward FIPS-197 AES-128 implementation compiled at -O0 with a runtime key schedule. The S-box is a 256-byte table in memory, so the first round performs 16 byte-wise table lookups whose addresses depend on the plaintext and the key.

static void sub_bytes(u8 s[16]) {
    int i;
    for (i = 0; i < 16; i++) s[i] = sbox[s[i]];
}

A memory-mapped trigger is asserted immediately before the first-round sub_bytes call and cleared immediately after it. The resulting window measures 1,865 target cycles (186.5 µs), which is 7,460 ADC samples at 40 MS/s. A full encryption takes 181,088–181,096 cycles depending on the data-dependent xtime branches.

The balanced schedule makes each CPA hypothesis uniform across the dataset and lets one acquisition attack all 16 key bytes. The two schedules were generated independently and verified to share no plaintexts.

Leakage model and CPA

Each key byte is ranked independently with the Hamming-weight S-box model HW(SBox(plaintext[i] XOR candidate)). The correlation is computed over the full recorded first-round window (samples 0–7,459) for all 256 candidate byte values. No alignment, filtering, or other preprocessing is applied.

Results are reported over a prefix grid fixed in advance: 16, 32, 64, 96, 128, 256, 512, and 1,024 traces. Disjoint 512-trace halves are ranked separately as a corroboration check. Candidate selection never reads the reference key; the key is compared only after the ranking is final.

Acceptance is based on ciphertext reproduction, not on correlation alone: every captured plaintext is re-encrypted with a self-contained AES-128 implementation using only the recovered key and compared with the ciphertext recorded at capture time.

No byte showed an exact top-score tie. The 16 winners were rank one at the full trace set in both sessions, and the recovered key matched the public reference key only when compared after ranking.

Leakage localisation

The winning correlation peaks occur at ADC samples 672, 1,108, 1,544, …, 7,212 in both sessions — 16 peaks spaced by exactly 436 samples. At 40 MS/s that is 10.9 µs, or 109 target cycles at 10 MHz. The SubBytes window contains 16 byte-wise table lookups in 1,865 cycles, about 117 cycles per byte, so the peaks line up with the S-box accesses.

Identical peak positions across two disjoint plaintext sets indicate that the observed structure belongs to the code and board rather than to a particular dataset. The result does not by itself identify a specific instruction or physical leakage mechanism.

Reproducibility and hold-out

Session 2 repeated the full bring-up: USB reset, bitstream programming, a fresh capture process, and a plaintext schedule with no overlap with session 1. It recovered the same 16 bytes at the same 96-trace prefix and reproduced all 1,024 ciphertexts.

A separate hold-out set of 16 plaintexts (seed 20261122) was verified absent from both attack schedules and captured with the same image. Re-encrypting those plaintexts with the recovered key reproduced 16/16 hold-out ciphertexts. The hold-out verification record reports identical SHA-256 values for the recovered and reference keys and no mismatches.

Limitations

  • One board, one bitstream, one public key, one clock frequency, and one gain setting; the result is not a claim about other configurations.
  • First-order CPA with a single leakage model and no preprocessing; aligned, filtered, or higher-order analyses were not evaluated.
  • No instruction-level attribution beyond the measured peak spacing.
  • Taking a maximum over many samples and 256 candidates can produce chance peaks; ciphertext reproduction and two-session agreement are the safeguards here.
  • Ciphertext reproduction proves that the recovered key is the key the device used for these captures. It does not prove generalization across sessions, devices, or keys.
  • No protected implementation was measured, so no countermeasure claim is made.
